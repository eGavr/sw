# Правила архитектуры

## Слои и зависимости

Поток вызовов и данных направлен от транспорта к внешнему backend-у:

```text
presentation -> use case -> repository -> data source -> external backend
```

При сборке приложения реализации зависимостей передаются в обратном направлении:

```text
presentation <- use case <- repository <- data source <- external backend client
```

Доменная модель не является отдельным шагом этого пути: use case, repository и data source обмениваются доменными объектами, а бизнес-решения остаются в `domain`.

Соблюдай следующие границы:

-   `presentation` зависит от application-слоя и транспортных библиотек. Он вызывает use case, но не обращается напрямую к репозиториям и data source-ам.
-   `application/use-cases` получает репозитории через конструктор и работает с возвращаемыми ими доменными объектами. Use case не обращается напрямую к data source, внешнему клиенту или transport-типу (request-модели/presenter-у).
-   `data/repositories` зависит от домена и data source-ов. Репозиторий объединяет данные нескольких backend-ов, если это нужно для одной доменной сущности.
-   `data/data-sources` предоставляет репозиториям доступ к данным доменных сущностей в конкретном backend-е. Data source использует клиент этого backend-а и не вызывает data source другого backend-а.
-   `domain` содержит бизнес-правила, выраженные через сущности, value objects и специализированные коллекции, а также доменные ошибки. Он не зависит от `application`, `data`, `presentation`, транспортных контрактов, клиентов и фреймворков.
-   `bootstrap.ts`, `compose-*.ts`, фабрики и entrypoint-ы являются composition root: только здесь допустимо знать сразу о нескольких слоях и связывать реализации.
-   Код в `packages/` должен быть переиспользуемым и не зависеть от конкретного сервиса из `services/`.

## Домен

-   Доменная сущность инкапсулирует состояние, инварианты и бизнес-поведение. Изменяй её состояние через методы, которые выражают бизнес-намерение и сохраняют инварианты, а не напрямую через поля.
-   Методы сущностей и доменных коллекций синхронны. В домене запрещены `async`/`await`, I/O, сетевые вызовы, таймеры и обращения к хранилищам.
-   Условия, арифметика, агрегирование и обход коллекции доменных объектов, реализующие бизнес-правило, должны находиться в сущности или специализированной доменной коллекции.
-   Связанные объекты и коллекции изменяй через методы, выражающие намерение. Не отдавай наружу изменяемые массивы, `Map` и внутреннее состояние.
-   Протокольные значения по умолчанию, protobuf-типы, `field_mask`, `*_UNSPECIFIED`, имена из генератора и backend-specific DTO не должны попадать в домен.
-   Общие доменные ошибки размещай в `domain/common/error`. Ошибку, специфичную для сущности, размещай рядом с ней в `<entity>/error/` и наследуй от подходящей общей доменной ошибки.

## Use cases

-   Один use case описывает один пользовательский или системный сценарий.
-   Основной метод use case-а оркестрирует шаги: получить сущности через репозитории, вызвать их синхронные методы, сохранить результат через репозитории.
-   Не переноси в use case бизнес-условия, вычисления и обход доменных коллекций. Перенеси их в сущность или доменную коллекцию.
-   Допустимы только сценарные ветвления: found/not found, create-or-update и диспетчеризация в один выбранный обработчик.
-   Не вызывай последовательно несколько вложенных use case-ов. Use case-диспетчер может выбрать по типу события или параметру ровно один use case и передать ему выполнение.
-   Объявляй параметры через `type ...Params` с `readonly`-полями. Не используй transport-тип (request-модель) или сгенерированные protobuf-классы как параметры use case-а.
-   Возвращай доменный результат: сущность, value object, доменную коллекцию или `void`. Не возвращай protobuf-message, результат `toObject()` или тип ответа внешнего клиента.
-   Проверку формата transport message выполняй в presentation request-модели/adapter-е, доменные инварианты — в сущностях и value objects.
-   Use case не управляет транзакциями БД и не знает о них: атомарность обеспечивают репозиторий и data source. Не вводи Unit of Work, который держит репозитории и запускается из use case, — это протечка persistence-паттерна в доменный сценарий. Кросс-агрегатную согласованность выражай отдельными сценариями или доменными событиями, а не одной широкой транзакцией.

## Репозитории

-   Репозиторий представляет хранилище одной доменной сущности или агрегата. Имя `<X>Repository` допустимо, только если `X` — реальная доменная сущность/агрегат.
-   Application-слой получает и сохраняет доменные сущности только через репозитории. Сведение данных из разных backend-ов выполняет репозиторий, а не use case и не data source.
-   Публичные методы репозитория должны иметь семантику хранилища: `get`, `find`, `list`, `create`, `update`, `save`, `delete`, `with` и осмысленные варианты `*All`, `*Many`, `get<Sub>`/`list<Sub>`.
-   Не добавляй в репозиторий сценарные команды вроде `execute`, `send`, `start`, `stop`, `trigger`, `issue` или проверки бизнес-политик и не создавай для них отдельный `application-port` или другой обходной интерфейс. Даже если сценарий является побочным действием, представь его как создание или сохранение подходящей доменной сущности либо события через `create`, `createMany`, `save` или `saveMany`.
-   Репозиторий не содержит бизнес-решений сущности и не экспортирует наружу типы конкретного клиента или backend-а. По сути в репозитории нет логики — только сборка доменной сущности из данных одного или нескольких data source-ов (и обратно при записи); вычисления/предикаты остаются в домене.
-   Репозиторий не открывает транзакции сам — делегирует их data source-у. Для сценария «прочитать агрегат под локом → изменить доменными методами → сохранить атомарно» допустим метод `with(id, cb)`, где лок и транзакция инкапсулированы в data source.

## Data sources

-   Data source предоставляет репозиторию доступ к данным или части данных конкретной доменной сущности или агрегата, которые хранятся в одном backend-е. Протокол и API внешнего backend-а инкапсулирует клиент, используемый внутри data source-а.
-   Размещай основной адаптер как `data/data-sources/<backend>/<entity>-data-source.ts`. Клиенты, DTO, mapper-ы и прочие детали реализации backend-а размещай во вложенных папках этого backend-а.
-   Называй data source по обслуживаемой сущности или агрегату, а его публичным методам давай семантику хранилища: `get`, `find`, `list`, `create`, `update`, `save`, `delete` и их осмысленные варианты `*Many`/`*All`. Не добавляй в публичный API data source-а сценарные команды; операционные методы вроде `send`, `start` или `stop` оставляй во внутреннем клиенте внешнего backend-а.
-   Data source одного backend-а не импортирует data source другого backend-а. Координация разных backend-ов находится в репозитории (транзакция между разными backend-ами невозможна — используй eventual consistency).
-   Транзакция — забота data source конкретного backend-а: открывай её внутри метода data source (напр. `dataSource.transaction(...)`), не поднимай транзакционную границу в репозиторий, use case или presentation. Атомарно пишется один агрегат целиком; если его данные лежат в нескольких таблицах/data source-ах ОДНОГО backend-а, координируй их в одной транзакции — data source, владеющий записью агрегата, может принимать `DataSource | EntityManager` и создавать дочерние data source-ы того же backend-а, привязанные к транзакционному manager-у.
-   Граница агрегата — про запись/консистентность, а не про чтение: для точечных проверок (например, авторизации) делай узкий targeted-запрос, не загружая весь агрегат.
-   Не пропускай backend-specific данные и ошибки в application/domain. Преобразуй их на границе data-слоя; для однотипных ошибок предпочитай общий mapper/decorator существующему копированию `try/catch` с разбором кодов.
-   **Data source не содержит доменных вычислений** — только маппинг данных и вызов клиента/бэкенда. Бизнес-предикаты (напр. «живо ли окружение» — фильтр по свежести хартбита/порогу, набор «свободных» состояний) формирует **домен** и передаёт готовыми (cutoff-таймстемп, критерий, список допустимых состояний), а data source лишь транслирует их в запрос. Пороги и правила живости/занятости в SQL/клиенте data source-а хардкодить нельзя.

## Presentation и транспорт

-   Handler принимает transport message, преобразует его в params use case-а, вызывает ровно один use case и преобразует доменный результат обратно в transport message.
-   В handler-е не должно быть бизнес-логики, обхода доменных коллекций или координации репозиториев. Допустима только обработка ошибок и условий, специфичных для транспорта.
-   Для gRPC сохраняй существующую структуру `presentation/server/grpc/services/<scope>/<version>/services/<service>/handlers/`; она должна зеркалировать scope, версию и сервис protobuf-контракта.
-   Для protobuf-транспорта скрывай все особенности protobuf (значения по умолчанию, enum-значения `*_UNSPECIFIED`, generated API, преобразование request/response) во входной request-модели и в presenter-е, а не в use case или домене.
-   Различай два транспортных класса по роли (не называй их обобщённо «DTO» — DTO по Фаулеру это тупой контейнер без поведения; наши классы несут поведение):
    -   входящее сообщение — **request-модель**: класс с валидацией формата транспорта; файл `*-request-model.ts`, класс `*RequestModel`.
    -   исходящий результат — **presenter**: класс с методом `present()`, который превращает доменный результат в wire-форму (реализует интерфейс `Presenter`); файл `*-presenter.ts`, класс `*Presenter`. Собственно «DTO» (плоский объект на проводе) — это результат `present()`, а не сам класс.
-   Request-модели и presenter-ы одного handler-а держи рядом с ним (папка `io/`), общий presenter/request-модель поднимай только до ближайшего общего уровня.
-   Не передавай сгенерированные transport-типы в application/domain и не заставляй доменные сущности знать, как строится ответ конкретного протокола.

## Стиль

-   Не пиши очевидных комментариев. Комментарий нужен только там, где код сам по себе плохо читается или где важен неочевидный «почему»; если код понятен без комментария — комментария быть не должно. Не описывай комментарием то, что и так видно из имён и структуры.

## Утилиты и общий код

-   Не выноси бизнес-логику сущности в безымянный `utils`/`helpers`-модуль. Она должна быть методом сущности, value object или доменной коллекции.
-   В service-level `utils` допустимы только действительно общие для сервиса функции, не знающие о конкретной доменной сущности.
-   Код, переиспользуемый несколькими сервисами и не содержащий их бизнес-правил, размещай в тематическом модуле под `packages/`, а не в свалочном `common`.

# Домен проекта (sw)

`sw` — внешняя реализация сервиса «облако окружений для W3C/WebDriver и Appium трафика» (референс функциональности — внутренний SurfWax, код не переносим). Принятая доменная концепция:

-   **Compute Provider (compute backend)** — абстрактный порт, подключаемый пер-инсталляцию (провайдер-фабрика по конфигу, как `AUTH_STRATEGY`). Умеет **по запросу поднимать и гасить окружения**. Реализаций может быть сколько угодно; в будущем вместо локального подставляется облачный — просто адаптер под тот же интерфейс.
-   **Local (Docker)** — первая реализация. Одна локальная машина — единственный «кластер/провайдер ресурсов». Поднятие окружения = запуск docker-контейнера из предсобранного образа (например, linux нужной версии), в который **доустанавливается нужный браузер** (конкретная версия Chrome) → готовое окружение с WebDriver-эндпоинтом.
-   **Environment и Session — отдельные ресурсы; Environment создаётся явно, Session — аллокацией под capabilities:**
    -   **Environment** — где исполняется сессия: **устройство/контейнер с НАБОРОМ установленных приложений** (capability-стереотип, W3C WebDriver + Appium — `platform_name`/`platform_version`/`device_name` + набор `application_name`/`application_version`; браузер = частный случай Application). Занятость (`busy`) — свойство **окружения**, не приложения: сессия аллоцируется под одно приложение из набора, но занимает окружение целиком. *(Почему набор: реальное устройство держит несколько приложений; «один app = одно окружение» сломало бы 1:1-занятость.)* Пользователь создаёт окружение явным запросом; жизненный цикл **асинхронный**: `enqueued → preparing → executing → deleting` (+ терминальный `failed`, если провижн не удался). Воркер поднимает через compute; **`endpoint` и `executing` пишет internal-ручка при первом хартбите агента (регистрация), НЕ воркер**. Для Local — docker-контейнер.
    -   **Session** — запущенное приложение внутри окружения; W3C/WebDriver + Appium трафик. Создаётся запросом **с требуемыми capabilities** (без явного environment): сервис аллоцирует свободное `executing`-окружение со свежим хартбитом, подходящее под capabilities (Selenium-Grid-style match). **Одна активная сессия на окружение (1:1)** — арбитр сама нода (`SE_NODE_MAX_SESSIONS=1`), БД-`busy` — подсказка (без `allocation_id`/UNIQUE); оптимистичный pick+retry, на create-пути в БД не пишем. Окружение переживает сессию и переиспользуется.
-   **Жизненный цикл:**
    -   Сессия имеет «умный» idle-таймаут: пока в сессию идут запросы — не убиваем; если запросов нет — убиваем по таймауту. Также сессию можно убить явным запросом.
    -   После смерти сессии (явный kill или idle-таймаут) **окружение НЕ убивается**. Пока окружение уничтожается только явным запросом.
-   **Гарантированные, полностью известные ресурсы — без capacity-машинерии SurfWax.** Сервис всегда знает точный live-набор поднятых окружений/сессий и ограничен известным потолком провайдера. НЕ переносим: static slots, приоритетную очередь запросов, предиктивный автоскейл/warm-пулы, `coordinator`, `ordinator`.
-   **Не только браузеры (заложено в модели).** Мобильные приложения (Android/iOS через Appium) — первоклассный случай; обобщающее понятие — **Application** (браузер или мобильное приложение + версия). НО в первой локальной версии реализуем только **Chrome/linux (docker)**; для Android только закладываем возможность в абстракциях, ничего не собираем.
-   Примеры: Chrome 100 → Environment = linux-контейнер нужной версии с доустановленным Chrome 100, Session = WebDriver-сессия Chrome. Android (позже) → Environment = Android нужной версии на модели телефона, Session = запуск приложения через Appium.
-   Compute-backend — внешний backend: доступ к нему инкапсулирует data-source (`data/data-sources/compute/local/…`), а `EnvironmentRepository`/`SessionRepository` дают storage-семантику поверх. Домен про `local`/`docker`/`k8s` не знает.
-   **Источник правды о live-инвентаре — Postgres** (реестр окружений + занятость); compute (Docker/…) — исполнитель, который хранит связь `env id → контейнер` у себя, без завязки на docker в БД. *(Пересмотрено: раньше источником был провайдер. Полный дизайн — `docs/design/environment-lifecycle-and-allocation.md`.)* Liveness — по хартбитам (агент шлёт ~раз в 3с; окружение выбираемо, если хартбит ≤6с). Занятость `busy` **ставит хартбит агента**, не create-session. **Секрет сессии (wdSessionId) в БД/логи не кладём.**
-   **Три раздельных слоя идентичности/доступа** (полный дизайн — тот же design-doc):
    -   **authN (кто ты)** — `User(external_id, provider_type)`: один логин через внешний IdP.
    -   **наша authZ (что можно у нас)** — `Account` + `account_user_permission` (membership); проверяется **синхронно** в handler-е (`environment:create` и т.п.).
    -   **ресурс-подключения (external authZ)** — `ProviderAccount(account_id, provider_type, external_ref, credential_ref, state)`, N на аккаунт, отдельный агрегат (заменил неиспользуемый `AccountResourceProvider`); `environment.provider_account_id` — на каком облаке крутится. `ProviderAccount` — это *привязка аккаунта к провайдеру ресурсов* (связь + креды + состояние), НЕ описание самого провайдера. Выбор compute-адаптера переезжает из install-конфига `COMPUTE_PROVIDER` в per-account `ProviderAccount` (роутинг `env→account→providerAccount→адаптер`).
    -   **Авторизация к провайдеру = владение активным `ProviderAccount`; внешний доступ энфорсит сам провайдер на провижне** (воркер зовёт `compute.start(credential)`, reject → `failed`), а не синхронным «а можно?»-роундтрипом. Секреты `credential_ref` — в секрет-стор, не plaintext/в логи; для `local`/`docker` не нужны.
-   **Эндпоинт окружения кодируется в session id** (приём из SurfWax) → роутинг последующих WebDriver-команд stateless: любой инстанс прокси декодирует адрес окружения прямо из id и проксирует туда, без липкого состояния и lookup на каждую команду.
